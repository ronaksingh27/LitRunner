2. HOW REQUESTS REACH THE APP

Visitor enters the hostname
  -> DNS provides the VM public IP
  -> OCI network rules allow incoming traffic
  -> Ubuntu firewall allows incoming traffic
  -> Nginx receives HTTP on port 80 or HTTPS on port 443
  -> Nginx forwards to Next.js at 127.0.0.1:3000

systemd starts Next.js after boot and restarts it after failures.
Port 3000 stays bound to loopback; visitors use Nginx.
127.0.0.1 always means the machine running the command. On your Mac it means
your Mac; inside your SSH session it means the VM.

6. CONFIGURE NGINX

On a replacement VM, install Nginx if absent:
  sudo apt update
  sudo apt install nginx

Create /etc/nginx/sites-available/ashsovereign using sudo nano. This is the
initial HTTP configuration. After Certbot adds HTTPS, preserve its additions;
do not overwrite the file with this HTTP-only version.

server {
    listen 80;
    server_name theashsovereign.duckdns.org;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Enable it with a symlink only if that link is absent:
  sudo ln -s /etc/nginx/sites-available/ashsovereign /etc/nginx/sites-enabled/ashsovereign

An existing dangling link does not need recreation: create its missing target.
Check before applying changes:
  sudo nginx -t

Only after the configuration test succeeds:
  sudo systemctl enable --now nginx
  sudo systemctl reload nginx
  curl -I -H 'Host: theashsovereign.duckdns.org' http://127.0.0.1/

Expected before HTTPS setup: HTTP 200 with Nginx forwarding to Next.js.

7. DNS AND BOTH FIREWALLS

OCI Console: find the CURRENT VM public IP. Update DuckDNS to that exact IP.
Do not rely on old addresses in terminal history.

Mac:
  nslookup theashsovereign.duckdns.org

Compare the returned address with OCI. If an IPv6/AAAA record is configured,
it must also point to a working server; do not publish stale IPv6 records.

OCI Console: inspect the security lists/NSGs actually attached to this VM.
For a public IPv4 portfolio, allow stateful ingress with source ports left
unrestricted and these destination ports:
- TCP 22 from your current public IP /32, for SSH.
- TCP 80 from 0.0.0.0/0, for HTTP and certificate validation.
- TCP 443 from 0.0.0.0/0, for HTTPS.
Keep SSH restricted. Do not open port 3000 publicly.

VM: inspect the host firewall separately:
  sudo ufw status verbose
  sudo iptables -L INPUT -n -v --line-numbers
  sudo ss -lntp

Earlier failing host state: UFW inactive, but iptables INPUT had ACCEPT rules for
established traffic, ICMP, loopback, and SSH, then a catch-all REJECT at rule 5.
UFW being inactive does not mean iptables allows everything.

Only if the CURRENT rules still match that layout and no equivalent web rule
exists, insert the web allowance before the REJECT:
  sudo iptables -I INPUT 5 -p tcp -m multiport --dports 80,443 -m conntrack --ctstate NEW -j ACCEPT

Inspect the rules again. Do not repeatedly insert duplicates or reuse rule 5
if the ordering has changed. Keep the existing SSH session open and verify
a second SSH connection works before closing it.

Persist the intended rules using the host's existing firewall manager. For
the recorded iptables setup, if netfilter-persistent is already installed:
  sudo netfilter-persistent save

If absent, install iptables-persistent and review its save prompts, then save:
  sudo apt install iptables-persistent
  sudo netfilter-persistent save

Do not enable/reset UFW or flush iptables as a shortcut.

Verified lesson from this deployment: netfilter-persistent was already enabled,
but the first reboot restored rules without the web allowance. Restoring the
allowance fixed access; saving the rules and rebooting again preserved it.
An enabled persistence service does not automatically save every live change.

Mac, before retrying certificate issuance:
  curl -I --connect-timeout 10 http://theashsovereign.duckdns.org/

Expected: public HTTP 200 showing the portfolio, not just a local VM response.
If this fails, fix DNS, routing, listeners, or firewall rules before Certbot.

Symptoms encountered:
- Public access fails after reboot while services/local HTTP work: this
  occurred here because the 80/443 allowance was absent from the restored
  INPUT rules. Nginx still listened on both public web ports. Restoring the
  allowance before REJECT, saving with netfilter-persistent, and testing a
  second reboot resolved the issue. Do not blindly insert duplicate rules.
- nginx -t reports missing sites-enabled/ashsovereign: the symlink target
  file was missing. Create sites-available/ashsovereign, test, then reload.
- Local Nginx works, public HTTP fails: check the DNS target and both firewall
  layers. Local loopback requests can pass while remote traffic is rejected.
- Nginx returns 502: check Next.js service, port 3000, and Nginx error logs.
- Certbot connect timeout: HTTP-01 cannot reach the server. Establish public
  HTTP before retrying. Account registration alone is not certificate success.
- Bare next command not found: use npm start; npm adds local binaries to PATH.
- SSH froze during a build: resource pressure was suspected, not established.
  Check memory and kernel logs before claiming an out-of-memory failure:
    sudo journalctl -k -b -1 --no-pager --grep='Out of memory|Killed process|oom'
  Previous-boot logs may be unavailable. Do not copy macOS build output to a
  Linux VM without accounting for native dependencies and CPU architecture.

12. EXTRA KNOWLEDGE: DNS, PORTS, AND THE REQUEST FLOW

Default ports
The URL scheme determines the default destination port when none is written:
- http://example.com/ means HTTP on port 80.
- https://example.com/ means HTTPS on port 443.
- http://example.com:8080/ explicitly chooses port 8080.
- https://example.com:8443/ explicitly chooses port 8443.
These defaults are standardized conventions. The server must still have a
service listening on that port, and the firewalls must allow the connection.

DNS supplies the address, not the HTTP request destination port
The browser looks up the hostname to obtain an IP address, possibly using a
cached answer. It then connects to that server IP on the chosen port. The
HTTP request goes to the web server; it is not sent to the DNS server.

Starting with HTTP in this deployment
1. Browser resolves theashsovereign.duckdns.org to its public IP.
2. Browser connects to port 80 through the OCI and Ubuntu firewalls.
3. Nginx receives the HTTP request and returns 301 with an HTTPS Location.
4. Browser follows that location using HTTPS. Next.js does not handle the
   initial redirect request.

Why Nginx redirects
The Certbot command's --redirect option configures Nginx to redirect HTTP.
A typical generated directive is:
  return 301 https://$host$request_uri;
$host preserves the hostname; $request_uri preserves the path and query.
Inspect /etc/nginx/sites-available/ashsovereign for the actual generated
configuration. The exact deployed file contents were not pasted for review.

HTTPS flow for the current Nginx setup
1. Browser connects to the VM on port 443.
2. In a full TLS handshake, Nginx presents its certificate and proves it has
   the matching private key. The browser validates the certificate, and the
   two sides establish encryption keys.
3. Browser sends the HTTP request inside the encrypted TLS connection.
4. Nginx decrypts it and proxies it over local HTTP to 127.0.0.1:3000.
5. Next.js returns its response to Nginx.
6. Nginx encrypts the response for the browser, which decrypts and displays it.

  Browser <-- encrypted HTTPS --> Nginx <-- local HTTP --> Next.js
                                  :443                 :3000

CSS, JavaScript, and images can use the same browser-to-Nginx connection.
A certificate is not revalidated for every HTTP request. A new full TLS
handshake performs certificate authentication again; session resumption can
use previously established trust without exchanging the certificate again.

16. RUNTIME, WEB SERVER, AND REVERSE PROXY CONCEPTS

JavaScript, React, Next.js, and Node.js
JavaScript is the language. Browser JavaScript can interact with the page;
Node.js runs JavaScript outside the browser with different APIs, including
server-side filesystem and networking access. Same language does not mean
the same APIs or access privileges.
React describes UI using components. Next.js adds framework features such as
routing, builds, rendering, and a production server. Node.js is the runtime
executing that server. Websites can also be built with static HTML, server
rendered templates, or browser-rendered React; Next.js combines useful
capabilities but is not required for every website.

A concise answer to "What is a web server?"
A web server is software that receives HTTP/HTTPS requests from clients and
sends responses, such as web pages, images, redirects, or data. "Server" can
also mean a machine: here the VM is the machine, while Nginx and the Next.js
HTTP server are programs running on it.

Does "web" mean public?
No. HTTP servers can be public, private-network-only, or loopback-only. The
listening address, routing, and firewall rules determine accessibility.
- 127.0.0.1:3000: Next.js is reachable from the VM itself.
- 0.0.0.0:443: Nginx listens on all local IPv4 interfaces, but public access
  still requires a routable address and permission through both firewalls.

Is Nginx a web server or reverse proxy?
Both. It is web-server software acting as a reverse proxy for the app. It is
also the TLS termination point and handles the HTTP-to-HTTPS redirect.
Nginx can serve static files, cache, and load-balance, but those roles were
not configured or verified here. The observed Next.js cache HIT header is
not proof of an Nginx proxy cache.

Can an app use multiple web servers?
Yes. Here Nginx listens on 80/443 and Next.js on 3000 on the same VM.
Nginx stays in the middle of every proxied request and response, not just
connection setup. The browser's HTTPS connection and Nginx's local HTTP
connection to Next.js are separate connections. Only Nginx handles TLS in
this setup. For a redirect, Nginx answers directly without calling Next.js.

Processes and commands
- nvm install/use reads the version in the current repository's .nvmrc.
- npm ci installs the lockfile's dependency tree reproducibly.
- npm run build generates production output under .next.
- npm start invokes next start; npm adds local node_modules/.bin to PATH.
  Bare next not found does not mean an unrelated Ubuntu package is needed.
- systemd runs the app independently of an interactive SSH terminal.
- enable configures startup at boot; start runs now; restart stops/starts;
  daemon-reload rereads unit definitions after unit-file edits.
- A system service does not automatically load interactive nvm shell setup,
  hence the explicit absolute Node path in ExecStart.
- nginx -t checks configuration; reload applies a valid changed configuration.

17. FIREWALL REASONING FROM THE ACTUAL FAILURE

The failing INPUT chain was evaluated top to bottom:
1. ACCEPT RELATED,ESTABLISHED traffic.
2. ACCEPT ICMP.
3. ACCEPT traffic arriving on loopback (lo).
4. ACCEPT NEW TCP connections to SSH port 22.
5. REJECT everything else.

A terminal ACCEPT or REJECT ends evaluation. The chain's default ACCEPT
policy applies only when no earlier rule has decided the packet. The catch-
all REJECT prevented new web connections from ever reaching that policy.
Local curl succeeded through the loopback rule; remote HTTP/HTTPS failed.

Connection tracking vocabulary
- NEW: traffic starting a tracked connection; a new SSH connection needed
  the port-22 rule, and new web connections needed a port-80/443 rule.
- ESTABLISHED: traffic belonging to a tracked connection, including later
  SSH packets and replies to a connection initiated by the VM.
- RELATED: traffic related to another tracked connection, such as certain
  ICMP errors. It does not mean arbitrary new traffic is trusted.
INPUT handles traffic delivered to the host; OUTPUT is a separate chain.

Why two firewall layers?
OCI security lists/NSGs regulate traffic in the cloud network. Ubuntu's
firewall regulates it on the VM. Permission at one layer does not bypass the
other. Earlier OCI rules restricted web access to one source IP, which could
exclude visitors and certificate validation servers. Final rule contents were
not supplied, even though the successful public and renewal tests demonstrate
that their tested paths became reachable.

Why saving mattered
iptables changes the running kernel rules. netfilter-persistent restores saved
rules at boot. A service can be enabled and successfully load an outdated
ruleset. Saving after the intended change and testing after a reboot proved
persistence in this exercise. active (exited) is normal for a one-shot service
that finished loading rules; it need not remain a continuously running process.

18. CERTIFICATES: ISSUANCE, KEYS, TRUST, AND RENEWAL

Issuance: Certbot and Let's Encrypt have different jobs
Certbot is the ACME client on the VM. Let's Encrypt is the certificate
authority. Certbot normally creates the website's private/public key pair
locally. The certificate request contains the public key; the corresponding
private key stays on the VM. The ACME account key is separate from the
website's TLS key. Registering an ACME account does not issue a certificate.
Source: https://letsencrypt.org/how-it-works/

For the HTTP-01 method used here:
1. Let's Encrypt supplies a challenge token.
2. Certbot arranges for Nginx to serve a response derived from the token and
   ACME account key at a special /.well-known/acme-challenge/ URL.
3. Let's Encrypt independently resolves the hostname and requests that proof
   over port 80. Nginx serves the proof; it does not solve a puzzle itself.
4. Successful validation authorizes certificate issuance. The CA signs a
   certificate for the hostname and public key.
The first attempt timed out while retrieving the proof. Later issuance and
renewal simulation succeeded. Keep port 80 reachable for this method; do not
keep retrying issuance while the required endpoint cannot be reached.
Source: https://letsencrypt.org/docs/challenge-types/

Public certificate versus secret private key
A certificate contains identity names, a public key, validity information,
and an issuer signature. It can be shared publicly. The private key must
remain secret. Nginx's privileged master can load protected key files.
fullchain.pem contains the website certificate and intermediate chain;
privkey.pem contains the secret key. Never paste or commit the private key.

The domain/IP relationship
A DNS-name certificate binds hostname(s) to a public key, not to one fixed IP.
Changing the server's IP does not by itself invalidate that certificate/key.
A hostname can have several valid certificates/keys, and a certificate can
cover multiple names. Domain validation proves domain control, not that the
website's content or operator is honest. DNS-account compromise can enable
fraudulent domain validation; HTTPS is not a cure for account takeover.

How the browser obtains the public keys and checks trust
- Website public key: in the website certificate sent by Nginx.
- Intermediate CA public key: in its certificate, normally sent by Nginx.
- Trusted root CA public key: in the browser/OS trust store on the visitor's
  device. Trust comes from that store, not from a root supplied by the server.
The browser verifies the website certificate's signature using the issuer's
public key, then follows the chain to a trusted root. It also checks dates,
constraints, and usage. Multiple intermediate layers are possible. A root's
self-signature alone does not establish trust.
Source: https://www.rfc-editor.org/rfc/rfc5280.html
The browser additionally checks that the requested hostname is covered.
These signature checks are local calculations. Some clients may retrieve
missing intermediates; revocation mechanisms may involve network access.
There is no required per-request "please approve this" call to Let's Encrypt.

Proof of possession and encrypted traffic
A copied public certificate is insufficient to impersonate the server. During
a full TLS 1.3 handshake, the server signs handshake data with its private key;
the browser checks that proof with the certificate's public key. The handshake
establishes traffic-encryption keys. The certificate itself is not the shared
secret used to encrypt every response. Ordinary server TLS authenticates the
server to the client, not the visitor's identity to the website.
Source: https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.3

Renewal versus browser verification
Renewal obtains a replacement certificate through the CA. A browser handshake
validates the certificate and server it encounters; it does not renew it or
repeat HTTP-01. Certbot's timer periodically checks whether renewal is due;
each timer run need not issue a certificate. A dry run exercises renewal with
test infrastructure. Its success plus a scheduled timer is useful evidence,
but an actual future production renewal remains to be observed.

19. CONNECTION REUSE AND COMMON MISUNDERSTANDINGS

When is the certificate checked again?
- More HTTP requests over an existing connection: no new certificate exchange.
- Refreshing the page: may reuse the connection; not necessarily a new check.
- A new connection using accepted TLS resumption: can authenticate from the
  earlier shared state without exchanging the server certificate again.
- A new full handshake, for example when resumption is unavailable, expired,
  or declined: certificate authentication happens again.
There is no universal "check every five minutes" rule. New connections may
be needed after idle closure, network changes, or server/client closure.
Each encrypted record still receives integrity protection. Existing TLS
connections do not redo certificate validation for every request.
Source: https://www.rfc-editor.org/rfc/rfc8446.html#section-2.2

Useful analogy
DNS gives directions to the shop. A certificate is a signed ID for the shop's
name. The private-key proof shows that the shop has the secret matching that
ID. The browser's trusted roots are its pre-established trusted issuers.
This analogy explains trust; the real checks use cryptographic signatures.

Other clarified distinctions
- A hostname identifies the site; its URL scheme chooses the default port.
- A domain registration, DNS hosting, VM, and TLS certificate are different
  resources. DuckDNS supplied a subdomain; no custom domain was purchased.
- HTTPS protects browser-to-Nginx traffic here. The loopback hop uses HTTP.
- Local success does not prove public routing/firewall success.
- Service active does not prove it starts at boot; enabled does not prove the
  application successfully recovered. Test actual public access after reboot.
- A HEAD request (curl -I) checks response headers. A browser GET also fetches
  content and assets. Successful HEAD is not full visual verification.

20. TROUBLESHOOTING DECISION TREE

Start with the smallest boundary that can fail. Inspect before changing rules.

A. Can the VM serve the application locally?
   curl -I --max-time 5 http://127.0.0.1:3000/
   If no: check systemctl status ashsovereign, journalctl, build output,
   WorkingDirectory, ExecStart, Node path, and ss -lntp. Fix this layer first.

B. Can Nginx reach it?
   sudo nginx -t
   sudo systemctl status nginx --no-pager
   curl -I -H 'Host: theashsovereign.duckdns.org' http://127.0.0.1/
   With HTTPS configured this may return a correct redirect. To test the
   encrypted virtual host locally with its correct name:
   curl -I --resolve theashsovereign.duckdns.org:443:127.0.0.1 https://theashsovereign.duckdns.org/
   If no: inspect listeners, the selected server block, proxy_pass, certificate
   configuration, and Nginx error logs. 502 commonly points to an upstream issue.

C. Does the hostname resolve to the intended VM?
   On Mac: nslookup theashsovereign.duckdns.org
   Compare against OCI. Inspect any AAAA record if IPv6 is also configured.
   A DNS answer alone proves neither HTTP reachability nor VM identity.

D. Does local work but public access fail?
   Inspect the attached OCI ingress rules, host iptables rule order/counters,
   Nginx bind address, and routing. Refusal and timeout are clues, not unique
   diagnoses. After a reboot, compare saved rules with the active rules.

E. Does HTTP work but HTTPS fail?
   Check Nginx's 443 listener, both firewall layers, nginx -t, certificate name,
   validity and chain. Do not use curl -k to declare a certificate check passed.

F. Does issuance/renewal fail?
   Read Certbot's exact error and /var/log/letsencrypt/letsencrypt.log. For
   HTTP-01, verify public port 80 and the challenge path. Confirm the renewal
   timer separately from a dry run. Avoid repeated blind issuance attempts.

G. Does an update or build freeze SSH?
   Memory pressure was plausible here but not proven. The earlier SSH trace
   connected at TCP level then timed out before the server's SSH banner; it
   did not establish a key/authentication error. Use OCI console access for
   recovery if all SSH sessions are frozen, then inspect memory/kernel logs.
   Neither swap creation nor the precise failure cause was confirmed.
   debug3 obfuscate_keystroke_timing lines are SSH-client debug messages.
   Do not install mailutils-mh/mmh/nmh for a missing Next.js command; those
   package suggestions concern unrelated executables named next.

21. REUSING THE SETUP FOR ANOTHER APPLICATION

Fill in an application-specific worksheet before adapting commands:
- Repository URL and approved deployment branch/commit.
- VM OS/architecture, SSH user, public address and account cost limits.
- App directory, runtime version, absolute runtime path, build/start commands.
- Unique systemd service name and local application port.
- Hostname and DNS records; public HTTP/HTTPS ingress requirements.
- Required environment variables, secrets, storage and database needs.
- Local/public health-check URLs and last-known-working release.

Reusable sequence
1. Verify machine resources, source, and pinned runtime.
2. Install, check, and build the actual app.
3. Start on a loopback port and verify the app directly.
4. Configure systemd for that runtime/path and verify service startup.
5. Configure an Nginx virtual host proxying to that port.
6. Match DNS to the intended server and allow web traffic through both layers.
7. Verify public HTTP, issue TLS, and test HTTPS and redirect behavior.
8. Test renewal and its timer; persist host firewall changes.
9. Reboot and retest externally without manually repairing services/rules.
10. Record exact version, evidence, known limits, and update/recovery procedure.

Adaptation boundaries
The Node and next start commands are specific to this app. A Python service
needs its own interpreter/virtual environment/start command. Multiple apps
can share Nginx 80/443 using hostnames while listening on different local
ports. Inspect firewall positions instead of copying rule number 5 blindly.
For a static-only export, a Node server may be unnecessary, but that conversion
was not implemented here. Persistent data and database backup require their
own design; this portfolio's lack of a database does not generalize to all apps.

Operational limitations of this implementation
One VM is a single point of failure. Updates rebuild in place with downtime.
CI/CD, atomic releases, automated rollback, app monitoring/alerts, load
balancing, database backup, and disaster-recovery drills were not implemented.
An OCI monitoring-agent timer was visible, but that does not prove application
monitoring was configured. These are future options, not completed features.
